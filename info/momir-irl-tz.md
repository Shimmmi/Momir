# ТЗ: Momir IRL — приложение для печати случайных существ MTG на BLE-термопринтере

## 1. Общее описание

Мобильное приложение (Flutter, Android + iOS), реализующее формат Magic: The Gathering **Momir** в реальной жизни. Игрок выбирает конвертированную стоимость маны (CMC) существа, приложение выбирает случайное существо с этой стоимостью из локальной базы карт (данные Scryfall), рендерит карточку в виде изображения и отправляет её на печать на подключённый по Bluetooth (BLE) мини-термопринтер с автообрезкой.

Работает полностью офлайн после первоначальной синхронизации базы карт. Сервер не требуется — вся логика на устройстве.

## 2. Технологический стек

- **Framework:** Flutter (Dart), таргеты Android + iOS
- **БД:** SQLite через пакет `sqflite` (или `drift` для типобезопасности — на усмотрение исполнителя)
- **BLE:** `flutter_blue_plus`
- **Печать ESC/POS:** `esc_pos_utils_plus` для генерации байт-кода команд + `flutter_blue_plus` для отправки сырых байт в write-характеристику принтера (готовые пакеты типа `esc_pos_bluetooth` под Bluetooth Classic не годятся, если принтер BLE-only — уточнить у исполнителя после выбора конкретной модели принтера)
- **Рендер карточки:** `dart:ui` (Canvas) или пакет `flutter_widget_from_html` не нужен — рисуем напрямую через `CustomPainter`, экспортируем в `ui.Image` → `ByteData` (PNG/raw bitmap) для передачи в принтер
- **HTTP-клиент для разовой синхронизации:** `dio` или `http` — используется один раз при первом запуске / по кнопке "обновить базу карт" для скачивания bulk-data с Scryfall

## 4. Функциональные требования

### 4.1 Модуль синхронизации базы карт (Scryfall)

- При первом запуске приложение предлагает скачать базу существ (объясняет, что это разовая операция, ~несколько десятков МБ, нужен интернет)
- Источник данных: Scryfall Bulk Data API
  - `GET https://api.scryfall.com/bulk-data` → найти объект с `type: "default_cards"` (или `oracle_cards` — уточнить на этапе разработки, какой набор даёт нужные поля без дублей по печатям), взять его `download_uri`
  - Скачать JSON, распарсить, отфильтровать записи, где `type_line` содержит `"Creature"`
  - Для каждой карты сохранить: `id` (scryfall id), `name`, `mana_cost` (строка вида `{2}{U}{U}`), `cmc` (число), `power`, `toughness`, `oracle_text`, `colors` (массив), `image_uri_small` (для потенциального будущего фонового арта — на MVP можно не скачивать сами картинки, только текстовые поля)
  - Записать в локальную таблицу `creatures`
- Кнопка "Обновить базу карт" в настройках — повторяет процедуру, обновляет данные (например, после выхода нового сета)
- Показывать пользователю: дату последней синхронизации, количество загруженных существ
- Обработка ошибок сети — понятное сообщение, возможность повторить попытку

**Схема таблицы `creatures`:**

| Поле | Тип | Комментарий |
|---|---|---|
| id | TEXT PRIMARY KEY | scryfall id |
| name | TEXT | |
| mana_cost | TEXT | символьная строка маны, может быть NULL у некоторых существ (напр. carddraft leftovers) |
| cmc | INTEGER | конвертированная стоимость, округлённая до целого для фильтрации |
| power | TEXT | текстовое поле — в MTG бывает `*`, `1+*` и т.п., не всегда число |
| toughness | TEXT | аналогично |
| oracle_text | TEXT | текст способностей, может быть длинным, может быть NULL |
| colors | TEXT | JSON-массив цветов, сериализованный строкой |
| type_line | TEXT | полная строка типа (для отображения подтипов, напр. "Creature — Elf Warrior") |

### 4.2 Модуль выбора и печати существа (главный экран)

- UI: ряд кнопок/чипсов с числами маны 0–10+ (10+ объединяет всё, что 10 и выше, как в правилах Momir)
- Дополнительно (можно вынести в v2, но заложить в модель данных сразу): переключатель "любой цвет / ограничить цветом" — чекбоксы W/U/B/R/G
- По нажатию на число:
  1. Запрос к `CreatureRepository`: `SELECT * FROM creatures WHERE cmc = ? [AND colors фильтр] ORDER BY RANDOM() LIMIT 1`
  2. Если результатов 0 — показать сообщение "существ с такой стоимостью маны нет в базе" (не должно случаться для 0-10 при полной базе, но нужно на случай пустых/неполных фильтров по цвету)
  3. Переход на экран предпросмотра карточки с выбранным существом
- Экран предпросмотра:
  - Показывает сгенерированный макет карточки как она будет напечатана (тот же рендер, что уйдёт на принтер)
  - Кнопка "Напечатать"
  - Кнопка "Ещё раз" (перевыбрать случайное существо с той же стоимостью, если результат не понравился — по желанию, это отход от канона Momir, но полезно для UX; можно обсудить с заказчиком, включать ли эту кнопку в MVP)
  - Индикатор состояния печати (идёт печать / готово / ошибка)

### 4.3 Модуль рендеринга карточки

- Реализовать как `CustomPainter`, рисующий на канвасе шириной, соответствующей ширине ленты принтера в пикселях (для 58мм при 203 dpi — 384px; вынести это число в конфиг, зависящий от выбранной модели принтера)
- Макет (сверху вниз):
  1. Имя существа — жирный шрифт, авто-уменьшение размера если не влезает в ширину
  2. Мана-стоимость — либо цифрой (`CMC: 3`), либо (v2) мини-иконками символов маны, если будут подготовлены битмап-иконки W/U/B/R/G/generic
  3. Разделительная линия
  4. Тип карты (`type_line`)
  5. Текст способностей (`oracle_text`) — перенос строк, уменьшение шрифта при длинном тексте, ограничение максимальной высоты (обрезать с "…" если совсем не влезает — задать порог символов)
  6. Разделительная линия
  7. Power/Toughness внизу справа, крупным шрифтом
- Рендер только чёрно-белый (1-bit), без полутонов — использовать сплошную заливку и чёткие шрифты, дизеринг не нужен, т.к. арт на MVP не печатаем
- Результат — `ui.Image`, конвертируемый в формат, который принимает ESC/POS-кодировщик (обычно raster bitmap построчно)

### 4.4 Модуль подключения к принтеру (BLE)

- Экран сканирования: список найденных BLE-устройств поблизости (фильтровать по имени, если у выбранной модели принтера предсказуемый префикс имени, напр. `Printer_XXXX` — уточнить после выбора конкретной модели)
- Выбор устройства → подключение → сохранение MAC/идентификатора устройства в `SharedPreferences`, чтобы при следующих запусках подключаться автоматически без повторного сканирования
- Экран настроек принтера: показывает текущий подключённый принтер, кнопка "Тестовая печать" (печатает тестовый паттерн/текст "Momir test OK"), кнопка "Забыть принтер"
- Обработка обрыва соединения: показывать статус в UI (подключено/не подключено), пытаться переподключиться автоматически при потере соединения
- **Важно:** протокол печати (ESC/POS команды vs проприетарный catprinter-протокол GB01/02/03) зависит от конкретной купленной модели принтера — заложить в архитектуру абстракцию `PrinterProtocolAdapter` с двумя реализациями (`EscPosAdapter`, `CatPrinterAdapter`), чтобы можно было переключить поддержку без переписывания остального приложения. На старте разработки реализовать только тот адаптер, который соответствует уже купленному принтеру.

### 4.5 Модуль печати (orchestration)

`PrintService`:
1. Получает `ui.Image` карточки от рендерера
2. Передаёт в текущий `PrinterProtocolAdapter` для кодирования в байты команд принтера
3. Отправляет байты через BLE write-характеристику (учитывать MTU-лимиты BLE — большие изображения нужно бить на чанки по 20/182/244 байта в зависимости от согласованного MTU, с паузами между чанками, чтобы не переполнять буфер дешёвого принтера)
4. По завершении — команда обрезки (если протокол принтера её поддерживает; если автообрезка встроена в принтер аппаратно и срабатывает сама — этот шаг не нужен, уточнить по документации принтера)
5. Возвращает статус (успех/ошибка) в UI

## 5. Нефункциональные требования

- Приложение работает полностью офлайн после первичной синхронизации базы карт
- Время от нажатия кнопки CMC до начала печати — не более 1-2 секунд (случайная выборка из локальной SQLite должна быть мгновенной)
- Устойчивость к разрыву BLE-соединения в процессе печати — не должно быть краша приложения, показывать понятную ошибку и позволять повторить печать
- Поддержка Android 8+ и iOS 13+ (стандартные минимальные версии для актуальных BLE-пакетов Flutter — уточнить актуальные требования пакетов на момент разработки)
- Permissions: Bluetooth (и Location на Android, если требуется для BLE-сканирования на используемой версии Android — обработать корректный запрос разрешений с объяснением пользователю, зачем это нужно)

## 6. Пользовательские сценарии

1. **Первый запуск:** пользователь открывает приложение → видит экран приветствия → предлагается скачать базу карт → после успешной загрузки предлагается подключить принтер → сканирование → выбор → сохранение
2. **Обычная игра:** пользователь открывает приложение (принтер подключается автоматически, если был сопряжён ранее) → нажимает число маны → видит превью карточки → нажимает "Напечатать" → карточка печатается и обрезается
3. **Принтер не подключён:** пользователь нажимает число маны → приложение показывает превью, но кнопка "Напечатать" неактивна с подсказкой "подключите принтер" и ссылкой на экран настроек
4. **Обновление базы:** пользователь заходит в настройки → "Обновить базу карт" → видит прогресс → готово

## 7. Этапы разработки (предлагаемая последовательность для Cursor)

1. **Этап 0 — каркас проекта:** инициализация Flutter-проекта, структура папок по разделу 3, настройка зависимостей
2. **Этап 1 — база данных:** реализация `ScryfallSyncService` и `CreatureRepository`, экран синхронизации, проверка на реальных данных (должно быть загружено несколько тысяч существ)
3. **Этап 2 — главный экран без печати:** выбор CMC → случайная выборка → отображение существа как обычного текста (без финального дизайна карточки) — чтобы проверить логику выборки до того как заниматься версткой
4. **Этап 3 — рендер карточки:** `CustomPainter`, финальный макет, экран предпросмотра
5. **Этап 4 — BLE-модуль:** сканирование, подключение, сохранение устройства, тестовая печать простого текста/паттерна
6. **Этап 5 — интеграция печати карточки:** кодирование рендера в ESC/POS (или catprinter-протокол — по факту выбранного принтера), отправка чанками, обработка ошибок
7. **Этап 6 — полировка:** обработка edge-cases (нет существ под фильтр, обрыв связи, permissions), UI-полировка

## 8. Открытые вопросы (нужно решить до/во время разработки, зависят от конкретной модели купленного принтера)

- Точная модель принтера и её протокол (ESC/POS или проприетарный) — определяет, какой `PrinterProtocolAdapter` реализовывать первым
- Точное имя BLE-сервиса/характеристики для записи данных у купленной модели (обычно узнаётся через BLE-сканер типа nRF Connect на этапе технической разведки перед началом разработки конкретного адаптера)
- Нужна ли поддержка фильтра по цвету маны в MVP или только в v2
- Нужна ли кнопка "перевыбрать существо" на экране предпросмотра (отход от канона формата)
- Ширина ленты и, соответственно, разрешение рендера в пикселях — зависит от купленной модели (57/58мм)
